# 人脸 1:N 评测台（face-bench）

给 RK3588 选型用的一台"精度 + 速度"测试机。你喂给它：

- **底库**：单人大头照，几千张，**每张图一个人，文件名就是人名**（一人一个文件夹也行）
- **探针**：摄像头抓到的批次图，几张到几十张，**也是每张图一个人**，命名口径跟底库一样；
  偶尔混进一张里有好几个人的合影也接得住

它输出：认得准不准（Rank-1 / 误识 / 漏识 / 合影里旁人有没有被误放行）、每个环节花多少毫秒（检测 / 对齐 / 提特征 / 检索）、以及底库涨到 1 万 / 1.6 万时检索要多久。

不含活体检测。前端是纯静态页面，零构建、零 CDN、内网可用。推理层做成了可插拔，PC 上测出来的界面和指标口径，后期直接对着 RK3588 或安卓板子上的推理服务复用。

模型与路线是怎么选出来的（同一评测协议下的公开精度对照、逐条淘汰理由）见 [`docs/RK3588-方案筛选与排序.md`](docs/RK3588-方案筛选与排序.md)。

## 30 秒跑起来

```bash
cd face-bench
./run.sh                     # 自动建虚拟环境 + 装依赖 + 起服务
```

首次克隆下来 `models/` 是空的（ONNX 权重 180 MB+ 不进 Git），先补一次模型：

```bash
bash models/fetch.sh         # 只缺哪个补哪个，逐个校验 SHA256
```

浏览器打开 <http://127.0.0.1:8617> 。换端口：`PORT=9000 ./run.sh`。

已经装过一次、只想快点起：`SKIP_INSTALL=1 ./run.sh`。

底库默认是空的，直接进第 2 步灌自己的照片即可。想先拿公开数据集试手，随便找一个
"每人一个文件夹"或"一张图一个人"的目录，用第 2 步的**导入本机目录**导一遍就行。

## 图片怎么放（最容易踩坑的一节）

### 底库：一张图一个人（默认），也可以一人一个文件夹

默认口径是**一张图一个人，文件名就是人名**：

```
底库/
  张三.jpg
  李四.jpg
  王五.jpg
```

一人多张照片时也可以按文件夹放，把"人员 ID 来源"切到"文件夹名"即可：

```
底库/
  张三/  1.jpg  2.jpg  3.jpg
  李四/  a.jpg  b.jpg
```

- "人员 ID 来源"默认**文件名即人名**（只去扩展名），另有：文件夹名（每人一个文件夹）、文件名去序号（`张三_0001.jpg`）、文件名前缀（按分隔符）、不自动判定。
- 没开始注册前界面就会显示"识别出 N 人"，规则选错当场能看出来；按文件夹认人时若整批只认出 1 个人（多半是把底库根目录当成了人名），注册完会在"需复查"里点名。
- 底库默认**一张图只取最大的那张脸**，避免把合影里的旁人存成这个人的模板。
- 每人建议 3~5 张模板；只有一张大头照也完全能用。
- 底库按模型分开存（`data/gallery_w600k_r50`），**换识别模型要重新注册一次底库**。

### 探针：也是每张图一个人，合影可以混着拖

```
探针/
  张三.jpg            # 平铺，文件名就是人名/工号（默认口径）
  cam1/李四.jpg       # 有批次目录也行，文件名照样先认
  cam1/王五_0007.jpg  # 带尾部序号也认得出王五
```

- 探针真值来源是**单独一个下拉**（默认"文件名即人名"，与底库同一套规则）：先拿文件名（连去掉尾部序号的形式一起）去底库比对，命中不了才轮到父目录名，**谁真正命中底库就用谁**。`cam1`、`20261106` 这类批次目录命中不了人，就不会被当成人名压过真名。
- 文件夹名**不在底库里**的图直接判成"非底库人员"，原始文件夹名保留在真值标签后面的括号里（如 `非底库人员(路人甲)`），方便回查是哪批人。
- 文件名是 `IMG_0001`、`1792052059096` 这类**相机自动编号**时不造假真值：没命中底库就留成"无真值"，靠你在结果页补标，免得一次选错规则把整批悄悄算成库外样本、把误识率带偏。
- **合影平铺在根目录**（不放进任何人的文件夹）时同理，真值为空，合影里的其他人靠你在结果页逐张脸手动补标。
- 合影里除了主体之外的脸默认**不认领真值**，但会被单独统计成"同框被放行"（见下面指标），这是合影场景最关键的一项。
- 探针里出现底库没有的人很正常，标成"非底库人员"就是专门测误识的样本，别删。

## 界面五步

**第 1 步 · 运行环境**
选识别模型 / 检测模型 / 推理线程；**推理后端**选"本机 ONNX"（PC 基线）或"远程推理服务"（RK3588、安卓板）。顶栏 6 个圆角标签实时显示系统、CPU 核数、后端、onnxruntime 版本、模型下载状态、当前底库规模。

**第 2 步 · 底库注册**
两种灌库方式，几千张优先用第二种：

- **拖进来 / 选文件**：把底库图片或文件夹拖进虚线框（或点按钮选）。上传是**一张一个请求**、4 路并行，
  请求体就是这张图的原始字节，所以哪一张失败只影响那一张，传到一半断掉也只退回那几张。
  点**开始注册**前会先发一个自检小包，确认这个浏览器真能把图片字节发出去——
  在应用内置的预览窗口里传大底库最容易栽在这一步。
- **导入本机目录**：把底库目录的完整路径填进输入框（访达里选中文件夹按 Cmd+Option+C 就是"拷贝路径"），
  点**导入本机目录**，服务端自己读盘注册。几千张不经过浏览器上传，实测 98 张 3.2 秒（约 30 张/秒），
  也不会撞上"当前窗口读不到磁盘"那类环境问题。支持 jpg / png / webp / bmp，含子目录，单次上限 3 万张。

两条路的认人规则、进度显示、"需复查"清单完全一致：默认只取每张图最大的一张脸，大头照里拍到的路人
会自动丢掉并记进"需复查"，不会静默吞掉。进度条走完后，每个人员一张带缩略图的卡片，显示模板数和
"眼球间距异常（疑似侧脸）"这类质量告警。
人员列表**分页加载**：默认每页 80 人（可切 40 / 200），列表上方是搜索人名 + 上一页 / 下一页 + 本页位置，
每页只从库里取那一页的人，3500 人的底库点开就是一屏，不用等浏览器画几千个格子。
每张人员卡片右上角有一颗 **✕**，只删这一个人（他的模板和头像一起走，别人一根毛不动）——
以前底库里混进一个错标的人只能清空整库重注册，几千张白跑。

**第 3 步 · 探针批次**
选探针处理方式（默认"自动"：先检测再对齐，一张脸都检不到时才退化成整图缩放）、探针真值来源（默认**文件名即人名**，与底库同口径）、检测输入尺寸（160 / 320 / 640，默认 320）、Top-K、判定阈值、合影识别策略（默认**每张脸都识别**）、忽略小于多少像素的脸、**评测并发路数**（1 / 2 / 3 / 4 / 6 / 8 / 12 / 16，默认 1）。拖入图片，点**开始评测**。
并发档位特意铺上 3 / 6 / 12 这些非 2 次幂：第 4 节扫出来的建议档经常正好是 3 路或 6 路，
下拉里没这一项就没法把建议原样填回来，只能挑个最近的，等于偷偷换了个配置去复现选型表。
点**把建议线程数填进第 1 节**时并发路数会一起对齐，缺档会在提示里说清楚。
探针上传和底库走同一套**一张图一个请求**（`/api/probe/open` → `push` → `close`）：几十张摄像头截图
不再拼成一个 multipart 大包，某张没传上去只影响那一张，评测照跑，结果出来时会明说"另有几张没传上来、
本批只评了几张"，不会悄悄少掉。按钮上会先显示"上传 12/40…"再显示"评测中…"。旁边的"历史批次"下拉可以回看以前跑过的批次，不用重跑；按钮上写着当前攒了几个批次，点**清空历史批次**一次删干净（报告 JSON 和探针原图一起删，底库不动）。
并发路数默认留在 1，因为 1 路是**延迟基线**：几张图就能看清 P50 该是多少。开并发是拿延迟换吞吐，
本机 30 张探针实测 1 路 13.0 张/秒（P50 57.6 ms）→ 4 路 25.4 张/秒（P50 135.0 ms）：吞吐翻倍，延迟涨到 2.3 倍。
所以先用 1 路量准精度和延迟，要到几路才划算交给第 4 步的并发扫描实测，别在这里瞎试。
批次参数（检测尺寸、Top-K、阈值、并发路数、最小脸）**开跑前就在服务端校验**，超范围直接 400 并说明
该填多少——不会跑到一半才失败，也不会静默把你填的值夹成别的数。下拉旁边另有一个**删除本批**：
只删屏幕上这一批（报告 JSON 与探针原图成对消失），删掉一次跑歪的评测不用把旁边几个好批次一起清空。

**第 4 步 · 并发 / 线程扫描（RK3588 选型）**
选型真正要定的不是"这块板子多快"，而是"**该开几路并发、给推理分几个核**"。这两个数互相牵制：
并发路数换吞吐、推理线程数换单帧延迟，只看一个点定不下来，得把「路数 × 线程数」每个组合
在同一批探针图上各跑一遍，摊成一张选型表。探针目录填服务端本机的路径
（和第 3 步「评测本机目录」填同一个就行），默认**等间隔抽样** 200 张（24~800：少于 24 张 P95 就是噪声，
再多原始字节一次吃不进内存），路数默认 1 / 2 / 4 路、线程默认「自动 + 4 线程」，单次最多 24 格
（每格都要把整批图重跑一遍）。
扫描会把第 3 节那套参数（检测输入尺寸、合影是不是每张脸都识别、判定阈值、真值来源）原样带进
每一格：以前只发路数和线程数，服务端只能退回默认值，于是把检测尺寸从 320 改成 160 再扫，
整张表一个数都不动，看着像「这块板子跟 det_size 无关」。
抽样张数、延迟可用线超出范围当场报错并说明该填多少，不会静默按上限跑一次几分钟的扫描。

省时间的关键是**每档线程数只重载一次模型**：线程数在建 session 时定死，换档必须重建后端
（重读两百多 MB 权重，本机 2~4 秒），但同一档下所有并发路数共用这个 session，
九格扫描只重载两次而不是九次。扫完把线程设置还原成你原来的值；中途有人改了就一直跑完、
不写回，免得把他的选择悄悄吞掉。
单次最多几格、并发路数最高几路这些上限由 `/api/env` 一并下发，界面按它算按钮该不该灰：
以前前端自己抄了一份常量，服务端为小板子把上限调低时界面不知道，
会把一格都没超的选择判成"超过上限"，或者反过来放行一个必被 400 的请求。

吞吐按**整格墙钟**算（含排队），不是 `1000/P50`。建议档先在"P50 不超过可用线"（默认 120 ms，可改）
的格里取吞吐最高，一格都不达标就退回吞吐最高并说明没有达标档。本机 Apple M5、`w600k_r50`、检测 320 实测：

| 推理线程 | 并发路数 | 吞吐 | P50 | P95 |
|---|---|---|---|---|
| 自动 | 1 | 12.9 张/秒 | 57.8 ms | 146.2 ms |
| 自动 | 4 | 24.2 张/秒 | 122.7 ms | 281.6 ms |
| 2 | 1 | 12.3 张/秒 | 58.9 ms | 151.9 ms |
| **2** | **4** | **24.5 张/秒** | **117.3 ms** | 292.8 ms |

2 线程 × 4 路的吞吐和放开线程跑一样，P50 还略低，并且给检测与业务逻辑留出多余的核——
所以建议档选了它。这类结论只有扫出来才看得见，本机一次几十秒，板子上更值得扫一次。
点**把建议线程数填进第 1 节**就直接套用。

**第 5 步 · 评测结果**
12 张指标卡 + 分阶段耗时表 + 阈值曲线 + 底库规模曲线 + 比对结果 + 易混淆对。
指标卡的张数会随着口径变化增减（「坏图 / 读不出」和拆成四档的「合影同框被放行」都是后加的），
所以这里只说清每一格的算法，具体数字看下面的口径表。

比对结果分两组，默认只看「比对成功」：命中的出**双图对照卡**（左边探针照片、右边底库留档照，中间是相似度），
没比对上的只出一行文字清单（文件名 + 最像的人 + 分数 + 没过线的原因），一万张探针也不会把浏览器压垮。
上方「本页 N 张：比对成功 X · 未比对成功 Y」是**图级互斥**口径（一张图只要有任意一张脸过阈值就算比对成功，
X + Y 恒等于 N；合影里一张命中的脸和一张没命中的脸不会再被重复计价），下面两栏的标题则按**实际列出的条数**
写——卡片按过阈值的脸数、清单按列出的行数，所以「150 张」和「N 张脸 / M 条」本来就不该相等。
合影里的旁人各算一条。卡片和清单上都留着标注入口（✓ 就是TA / ✗ 不在底库 / 其实在底库），
识别率靠这些人工标注算出来，改完立刻重算指标，不用重新推理。

两个交互值得单说：

- **阈值滑杆**：拖它不会重新推理，直接用缓存的 Top-K 结果重算，秒级刷新。先用默认阈值跑完批次，再拖滑杆找你要的工作点。
- **逐脸真值框**：合影里每张脸都能单独改真值，直接打几个字就从底库人名里筛候选（几千人的底库不会再给每条脸塞一个几千项的下拉框），也能选"非底库人员"。改完立刻重算全部指标，同样不重新推理。

## 指标口径（看数前务必读这一段）

同一批结果分两套口径同时给，别混着看：

| 指标 | 口径 | 说明 |
|---|---|---|
| **主体 Rank-1**（图级） | 每张有真值的图，**不含"非底库人员"** | 只看"主体那张脸"认对的比例 |
| **人脸级 Rank-1** | 所有已标真值的脸，同样剔除非底库 | 合影里每张脸都是独立样本，含手工补标的旁人 |
| **Recall@k** | 同上，图级 / 人脸级各一份 | 真值出现在 Top-k 里的比例，衡量**检索**质量。掉了就是底库缺人或特征不行，**调阈值救不回来**，所以拖滑杆时这一项不会动 |
| **检出率** | 图 | 检测器真正检出人脸的图占比。**整图兜底不算**：裁到草地、衣领的图没脸，也照样会被硬比一次，括号里单独告诉你有几张 |
| **图级误识 / 漏识** | 图 | 放行但认错（含非底库被放行）/ 没过阈值被拒（不含非底库，那是拒对了） |
| **合影同框被放行 N/M** | 脸 | 非主体的脸被认领成库内某人。**合影场景的核心风险项**。放行的还拆四档：认对旁人 / 认错人 / 非底库被放行 / 还没标注 |
| **非底库 正确拒绝 / 误放行** | 脸 | 标成"非底库人员"的脸：拒绝才算对，被认成库里某人就是误识。这两项加起来 = 标了非底库的脸数 |
| **误放率 FAR** | 脸 | 标为非底库的脸里被放行的比例（`far_estimated`）。**分母只有非底库脸**，别的脸进去就会算出 1250% 这种数。界面上直接写在「非底库 正确拒绝 / 误放行」那张卡的标签里，省得再拿计算器除一次；一张非底库脸都没有时显示 `—`，不装作 0% 很安全 |
| **P50 / P95 延迟** | 图 | 单张图端到端耗时。开并发时这一项必然变差，看吞吐就要同时看它 |
| **吞吐** | 图·脸/秒 | 按**整批墙钟**算（`throughput_basis="wall"`），含排队与并行；拿不到墙钟才退回按 P50 折算并标出来。分子只算**评完成的**图/脸，所以别拿「批次数 ÷ 墙钟」去对账，那个数会偏高 |
| **需复查坏图** | 图 | 读不出、解码失败、推理抛异常的图（`verdict="error"`）。**已从检出率与 Rank-1 的分母、以及吞吐的分子里剔除**（它们解码失败前花掉的时间仍留在整批墙钟里，所以吞吐只会偏保守不会虚高），没检到脸不算坏图；清单里这类行标「没评成」，不跟「没检出脸」混成一类 |

**"主体那张脸"是怎么定的**：在这张图的所有脸里，先看有没有"Top1 正好是真值、且分数已过阈值"的脸，有就把真值挂到其中分数最高的那张；一张都没有就退到检测框最大的脸。其余脸一律留空待标——合影里的旁人本来就不该被默认当成主体，否则人脸级指标会被凭空拉低。

改图级真值会重新自动分配；改单张脸真值只影响那一张。两条路径和拖阈值滑杆共用同一套重算函数，所以图级和人脸级永远不会打架。

**图级判定只看"整图真值 + 主体脸的 Top1"**，不直接抄主体脸的脸级结论。否则你在逐脸真值框里把主体改成"未标注"时，明明认对的人会被记成误识，误识表里还会出现"张三 → 张三"这种自相矛盾的条目。

**"非底库人员"是独立的一类真值**：库里根本没有这个人，所以期望结果是**不放行**。拒了记"正确拒绝"，认成库里某人记"误识"（进误识表，也进合影同框统计），但它永远不进 Rank-1 / Recall@k 的分母——那两项衡量的是"认人认得准不准"，跟库里没有的人无关。

**吞吐按整批墙钟算，不按 P50 折算**。以前是 `1000/P50`：一开并发每张图都在排队，P50 一起变差，
折算出来的吞吐反而比单路更低——越优化越慢，逼着人得出"别开并发"的错误结论。现在取整批墙钟
（`throughput_basis="wall"`），排队和并行都算在里面——同一批 30 张图 1 路 13.0 张/秒、
4 路 25.4 张/秒，先后顺序终于是对的。只有实在拿不到墙钟时才退回按 P50 折算，并把 basis 标成 `p50`
让你知道这个数是估的。

**坏图单独进"需复查"，不进分母**。解码失败、推理抛异常的图根本没有可用输入，算进检出率分母
会把好好的检测器冤枉成漏检。但**"检不到脸"不算坏图**——那是真实的漏检，必须留在分母里，否则检出率
永远 100%。有真值却一张脸都没检到的图照样算 Rank-1 失败（条数在 `n_rank1_nodetect` 里），
检测器越差分数越低，不会反过来变好看。
早先解码失败会被塞一张 112×112 纯黑小图继续往下跑，等于假装「这是张正常照片，只是没检出脸」：
`n_error` 恒等于 0，坏图全记成漏检，白跑一次推理还挤进分母，真值也没算、掉进「非底库」那一类
反过来污染 FAR。现在它如实是 `verdict="error"`，而且拖阈值 / 改真值都不会把它重算洗白——
重算只做比较，根本没评出来的那张就永远是没评出来。

**阈值建议是怎么给的**：冒认者分数按**人**抽（口径和检索的 `per_person` 一致——先抽一个人当探针，
再取他与另一个人的最高分），因为 `gallery_far_1e4` 的指数 9999 说的也是人；按模板对抽的话
每人模板越多就越低估"某个人被放行"的真实概率。抽样时每人模板要补齐成等长方阵，**补齐用的空槽不参与取最高分**：
空槽是整条 `-1.0`，模长不是 1，它和探针的点积等于 `-sum(探针)` 而不是某个余弦，本机用真实向量实测最高
能到 2.58、12.5% 的冒认样本超过 1.0，结果 FAR 虚高到阈值拉到 1.0 都压不住，满足 `far<=1e-4` 的档位整段消失、
推荐阈值退化成 `t=1.0 / TAR=0`，整栏「阈值建议」凭空没了——而只要有人模板数不一致就会触发，正是下面推荐的
"给几个人再补一张不同场合照片"会造出来的状态。配上库内同一人互配的 genuine 分布扫 TAR/FAR 曲线，
取万库规模下误报还受得住的最高 TAR 那一档。两个刻意的取法：

- **TAR 并列时取更高的那一刀**。TAR 相同意味着放行率一样，阈值越高冒认者越少。genuine 侧人多模板少时
  TAR 就是粗台阶，并列几乎必然：本机 4 个人有多张模板时实测连着 4 档并列，取 `t=0.5545`
  （FAR 3.5e-5，外推万库 0.30%）而不是 `t=0.5251`（FAR 8.5e-5，万库 0.57%）——放行率一样，误报减半。
- **反向的 1e-6 档取最低的 t**。那一档贴着"几乎全拒"，台阶顶端常连着几个 TAR=0 的点，
  取高的一档等于白亏一档召回。

**genuine 和冒认两侧都可以用探针真值补**。底库每人只有一张模板时（快速注册就是这个形态，
也是绝大多数底库的真实形态）底库内部永远凑不出同一人互配对，以前这一栏整片空白，
而提示语写的是"跑一批带真值的探针即可生成"——探针其实压根没参与计算，照着跑完 202 张
全标了真值的批次，那一栏还是原样一句话。现在一批标了真值的探针就是这两类样本：
真值人员命中 Top-K 的那一行是同人互配分（genuine），同一张脸对非真值人员的最高分是冒认分
（impostor），口径和检索的 `per_person` 完全一致，不用重新推理。界面会写明依据
（`basis`：`gallery` 还是 `gallery+probe`）以及两侧各来自哪里、多少条。三条刻意的处理：

- **真值没进 Top-K 的按删失处理**，只计数不补数。那张脸的同人分只知道"低于第 K 名"，
  随手补成第 K 名会系统性偏高，TAR 直接虚高。
- **没标真值的脸两侧都不进**（合影里没标注的旁人）：根本不知道他在不在库里，进哪侧都是编。
- **改一条真值就重算这一栏**。真值就是分布的原料，以前把真值一条条标全了那一栏还停在"样本不足"。

本机实测（98 人底库 / 202 张带真值探针 / `w600k_r50`）：`basis=gallery+probe`，
genuine 202 条全部来自探针，冒认 9708 条 = 底库抽样 9506 + 探针 202，推荐阈值 `t=0.5845`
（TAR 0.9901 / FAR 0）、1e-6 档 `t=0.3615`——改之前这一栏是 `curve: []`、`best: null`。

|---|---|---|---|
| `w600k_r50` | 识别（512 维） | 已就位，SHA256 校验通过 | buffalo_l 主力，公开榜 MR-ALL @FAR 1e-6 = **91.25%**，阈值先验 **0.4078** |
| `glintr100` | 识别（对照，512 维） | 已就位，SHA256 校验通过 | antelopev2 主力，ResNet100@Glint360K，MR-ALL @FAR 1e-6 = **90.66%**，特征耗时约 `w600k_r50` 的 1.7 倍 |
| `det_10g` | 检测 SCRFD-10GF | 已就位，SHA256 校验通过 | 精度优先 |
| `det_2.5g` | 检测 SCRFD-2.5GF | 已就位，SHA256 校验通过 | RK3588 Gundam 方案同款，速度优先，上板推荐；本机实测检测耗时约为 `det_10g` 的四成 |

下载：`bash models/fetch.sh`（清单和校验值以 `app/config.py` 为准，已就位就跳过，只缺哪个补哪个）。
`w600k_r50` / `det_10g` 走 hf-mirror 直链；`det_2.5g` 和 `glintr100` 官方只以 zip 发行，脚本按
HTTP range 只抽需要那一段（`det_2.5g` 取 3 MB 而不是 276 MB 整包），解出来的字节按 zip 中央目录里的
CRC 复核；GitHub 直连不稳时自动切 `ghfast.top` / `gh-proxy.com` 镜像。

两点提醒：官方模型表里 buffalo_m 与 buffalo_l 识别精度相同（都是 `w600k_r50`），差别只在检测器算力，
所以换 `det_2.5g` 只影响检测耗时和检出率，不影响识别精度上限。`glintr100` 的阈值**不能照抄 0.4078**：
它的余弦分布整体偏高（8 张无关脸两两相似度均值 0.24，最高一对已到 0.49，而 `w600k_r50` 是 0.18 / 0.39），
照抄同一阈值会更松、更容易误放行——换识别模型本来就要重新注册底库，顺手把阈值重标一遍。

阈值 0.4078 只是**起点**。最终阈值必须用你自己的底库和探针标定：跑完一批带真值的探针，拖滑杆找到"合影闯入率可接受、漏识最低"的那个点。

```bash
.venv/bin/python -m cli.run --gallery /path/底库 --probe /path/探针 \
    --rec w600k_r50 --det det_10g --det-size 320 --threshold 0.4078 --topk 5
```

人员 ID 默认自动判别：`--gallery` 下面还有子目录就按"每人一个文件夹"认人，平铺就按文件名认人。要强制哪种用 `--gallery-mode name|path|id_num|prefix|none`，探针对应 `--probe-mode-id`。

就交回整个文件名交给底库去命中——以前这些图被判成"推不出真值"，静默退出 Rank-1 分母，而检出率分母仍是全部图。）

命令行回归用的是**自己的**底库目录 `data/gallery_cli_<rec>/`，不会碰界面上登记的那份 `data/gallery_<rec>/`：
以前两者共用同一个目录，而注册前要先清库、清库是真的删文件，于是"在板子上跑一次命令行回归"等于把你在界面里
注册的几千人的底库整个清掉换成 `--gallery` 的内容。`--gallery` 目录里一张图片都没有（路径写错就是这样，它只安静地返回空）
会当场报错退出，而不是删完库再拿空库跑完整批探针、只打一行「0 人 / 0 模板」。

结果落到 `reports/cli_<时间戳>.json`。`cli.mkdemo` 可以把一个公开数据集切成"底库 + 探针"的目录结构，用来造测试数据。

改过指标或统计口径后，先跑这个自检（不加载模型，零点几秒）：

## PC 基线（Apple M5，10 核 CPU，onnxruntime 1.31.1）

98 人底库 / 202 张探针（含亮度姿态增强）实测：

- 注册：3.2 秒（30.8 张/秒）
- 检出率 100%，图级 Rank-1 **99.01%**，人脸级 99.01%，误识 0，漏识 2
- 同框脸 57 张，**全部拦下**（闯入 0）
- 吞吐 16.2 图/秒、18.3 脸/秒
- P50 端到端 61.9 ms = 检测 23.4 + 对齐 0.08 + 提特征单脸 34.2 + 检索单脸 **0.19**
- 检索曲线：8192 模板 → 0.71 ms，16384 → 1.80 ms

> 注：这组基线跑在「检出率」口径收紧之前。现在按整图兜底的图不再计入检出，
> 重跑同一批看板的检出率可能低于 100%，识别率不受影响。

**结论：万级底库的检索根本不是瓶颈**，涨到 1.6 万也就 1.8 ms。时间全在检测和提特征上，移植到 RK3588 时只需要盯这两个环节的 NPU 表现。

## 移植到 RK3588

评测台本身（HTTP 服务 + 前端 + 指标计算）纯 Python + numpy，可以直接跑在 RK3588-Ubuntu 上；要换的只有推理层。**上层检索和指标代码一行都不用改。**

### 形态 A · RK3588-Ubuntu，换本地推理后端

1. 板上装 `rknn-toolkit-lite2`（Runtime 库，PC 侧用完整版 `rknn-toolkit2` 转模型）。
2. 在 `app/backend.py` 里照 `OnnxBackend` 加一个 `RknnBackend`，只需实现三个方法：`detect()`、`embed()`、`info()`。
3. `build()` 里按 `kind == "rknn"` 分发，界面第 1 步的"推理后端"多一个选项即可。
4. 推荐组合：`det_2.5g`（INT8）+ `w600k_r50`（**先 FP16**）。
5. 转换红线：`w600k_r50` 的预处理是 mean 127.5 / std 127.5，**必须在转 RKNN 时折进量化参数**；`optimization_level=0`；验收标准是同一批对齐人脸在 ONNX 与 RKNN 下 embedding 的余弦最低值 ≥ 0.99。
6. 识别模型对量化敏感，INT8 要配校准集 + MMSE，且必须用你自己的底库重测 FAR/FRR。

### 形态 B · 安卓 / 混合部署，走远程推理

板子（安卓 App 或 Ubuntu 服务）只要暴露两个 HTTP 接口，PC 上这个评测台选"远程推理服务"填地址就能测：

```
POST /v1/detect  {image_b64, det_size, thresh, nms}
     -> {faces:[{box:[x1,y1,x2,y2], score, kps:[[x,y] x5]}], ms}

POST /v1/embed   {image_b64(112x112 对齐图), model}
     -> {vector:[512], ms}
```

契约细节见 `app/backend.py` 的 `RemoteBackend`。检索、指标、报告、改标全部仍在 PC 上跑，方便你和 ONNX 基线逐项对比。注意远程模式下 `ms` 含网络往返，看分阶段耗时表时把它和纯推理分开算。

### 绝对不能改的数值约定

换后端时这几条必须完全一致，否则精度会莫名其妙地掉：

- 识别输入归一化：`(x - 127.5) / 127.5`，输入 112×112，RGB 顺序
- 检测输入归一化：减 127.5、除 128.0
- SCRFD 三档 stride = 8 / 16 / 32，anchor 网格用 `np.repeat` 展开（不是 `tile`）
- 特征输出 512 维后做 L2 归一化，检索就是内积
- 对齐用 InsightFace 通用 5 点参考模板（`app/config.py` 的 `ARC_REF_LMK`）

```

    scrfd.py    SCRFD 检测后处理
    align.py    5 点对齐 + 质量评估
    gallery.py  底库（按模型分目录，SQLite 存人员与向量，分页查询）
    bench.py    探针批次、自动标真值、阈值重算
    metrics.py  Rank-1 / Recall@k / TAR-FAR 扫描 / 耗时分位数
    server.py   FastAPI 路由
  static/       前端（纯静态，无构建）
  cli/          命令行评测、测试数据生成
  models/       ONNX 模型
  docs/         选型依据（RK3588 方案筛选与排序）
  data/         底库缓存 + 探针原图            ← 可安全删除
  reports/      每个批次的 JSON 评测报告        ← 可安全删除
```

`data/` 和 `reports/` 是本地缓存，删了不影响功能。服务启动时会把 `reports/probe_*.json` 读回内存，所以历史批次重启后仍能在"历史批次"里打开、继续改标；探针图不在也不会把批次从下拉里抹掉：它照样能打开看指标和改标，只是结果卡顶上多出一行说明原图已不在（`images_gone`），免得一次手动清理就让十几分钟的评测结果整个看不见。

不想手动翻目录就在界面第 3 步点**清空历史批次**（接口 `DELETE /api/runs`）：内存批次、`reports/probe_*.json`、`data/probes/<批次>/` 整个目录（整图缩略图 `<i>.jpg`、对齐人脸 `<i>-f<j>.jpg`、清单 `meta.jsonl`）一起删，顺带扫掉只剩报告的孤儿和没人认领的死目录，删完告诉你释放了多少。探针向量只在内存里现算、从不单独落盘，所以批次没有别的特征文件要清；命令行的 `cli_*.json` 与底库的 `gallery.db`、`thumbs/` 都不在删除范围内。

只删一批用**删除本批**（接口 `DELETE /api/runs/<批次>`）：口径和清空全部完全一致，报告和
`data/probes/<批次>/` 必须成对消失，别的批次和底库一根毛都不动；删失败如实报 `failed`，
不假装删掉了。以前只有「清空全部」，阈值设错或选错目录跑歪一次，就得把旁边几个好批次一起删掉重跑，
而一万六千张探针要跑十几分钟。批次号在拼路径之前就用 `[0-9A-Za-z_-]{4,64}` 校验掉，
`../../etc` 这种传进来只会吃 400，不会变成任意目录删除。

底库是一个 SQLite 库，目录里只剩一个数据文件：

```
data/gallery_<模型>/
  gallery.db     人员 + 模板 + 识别向量（向量是模板行里的一个 BLOB 列，和人名同一行，永远不会错位）
  thumbs/        底库缩略图
```

模型 key 只含字母、数字、`_-.` 时目录就是上面这个名字（`data/gallery_w600k_r50`）。
远程推理模式的 key 是 `remote_<服务地址>`，而地址天生带斜杠，所以含其他字符的 key 会整体
转义成扁平的一层：`gallery_<8位摘要>_remote_http%3A%2F%2F10.0.0.9%3A8080%2Fv1%2Fembed`。
以前是把 key 直接拼进目录名，`http://10.0.0.9:8080/v1/embed` 会在 `data/` 下面一路建出
`gallery_remote_http:/10.0.0.9:8080/v1/embed/thumbs` 四五层以冒号结尾的目录，缩略图散在
里面、清库时容易只删掉最外层；地址路径里带一段 `..` 还能把整个底库建到 `data/` 外面去。
摘要后缀是为了两个只差末尾的服务不会因为名字截断而共用一个底库。

三张表：`persons(id, name)` 存人名；`templates(tid, person_id, vec, source, box, score, quality,
bad, thumb, dim, created_at)` 一条模板一行，识别向量就在这一行的 `vec` 列里；`meta(key, value)`
记模型和维度。用 SQLite 而不是自定义文件格式，是因为它不需要额外装任何服务进程（Python 自带
`sqlite3`），一个文件就是整个底库，拷走即备份，安卓和 Ubuntu 的 RK3588 上都是同一套代码。

注册时**每条模板当场落库**，攒够 200 条提交一次事务（逐条提交会让几千张底库慢一个数量级）；
库开着 WAL，后台在注册、前台照样能评测，两边不互相堵死。进程被杀、板子断电最多丢最后没提交的那几条，
绝不会出现"C 的向量配上 B 的名字"这种看起来合理的错答案。缺了归属的向量会被跳过，并在顶栏底库标签和
`/api/env` 的 `integrity` 里点名，提醒你重传那几张图。每次评测收尾会把 WAL 日志收拢回主库，
不让 `-wal` 文件在板子上悄悄涨到几百 MB。

老的 `features.npz` + `meta.json`（以及更早期的 `features.npy`）底库**不用重传**：启动时看不到
`gallery.db` 就自动迁库，核对条数一致后把老文件挪进同目录的 `legacy/` 存档，不删，随时能退回。

底库列表走**服务端分页**：`GET /api/gallery/list?page=2&size=80&q=张`。服务端一次 SQL 只取那一页的人，
搜索按人名模糊匹配（`%` 和 `_` 按普通字符处理，不会被当成通配符误命中），`total` 只数有模板的人。
探针页改真值要用的人名清单走 `GET /api/gallery/persons?names=1`，只回人名，几千人也才几十 KB。

界面第 2 步点**清空底库**（接口 `DELETE /api/gallery`）是整库连文件一起清：内存模板、`gallery.db`
（含 `-wal` / `-shm`）、`thumbs/`、`legacy/` 一次删光，删完不写回一个空库。缩略图必须跟着删——界面不再
引用它们，`/api/thumb/<名字>` 却还认得这些文件名，2400 张就是 9 MB，悄悄躺在板子的 eMMC 里最难查。
删单个人（`DELETE /api/gallery/person/<人名>`）同样只带走他自己的缩略图，顺带清掉已经没有模板的空人名行；
返回体里的 `thumbs_removed` 和 `freed_bytes` 就是界面提示"删了几张头像、释放多少"的来源。
界面上入口在底库列表：每个人那张卡片右上角有一颗 ✕（悬停会写明"只删这个人"），
混进一个错标的人不用再清空整库重注册几千张。**人名不在库里时报 404** 而不是回一句成功：
删除函数对不存在的人只返回 `persons_removed: 0`，照这弹「已删除」的话，
用户会看见"提示说删了、人还好好在列表里"，然后再也找不到他去哪了。

```bash
FACE_DATA_DIR=/mnt/nvme/face-data FACE_REPORT_DIR=/mnt/nvme/face-reports ./run.sh
FACE_LOG_LEVEL=info ./run.sh     # 默认 info，请求与异常 traceback 会进日志
```

## 常见问题

**底库显示"未注册"** — 页面刚加载或底库还没注册；刷新页面，确认顶栏"底库"标签的人数。

**底库列表里找不到某个人** — 列表是分页加载的，几千人不一次画完（默认每页 80 人）。用列表上方的搜索框直接搜人名，或按上一页 / 下一页翻过去；搜索等 0.3 秒再发请求，打字过程中人数看着不变是正常的。人名带 `%`、`_` 的按普通字符匹配。

**底库清空了，`data/gallery_<模型>/thumbs/` 里还堆着几千张图** — 老版本点"清空底库"只清内存模板和向量文件，缩略图留成了孤儿。现在再点一次**清空底库**就连图一起删掉（提示会告诉你删了多少张、释放多少），或者直接删 `data/gallery_<模型>/` 整个目录。

**底库传到一半断掉，最后显示「成功 0 个模板 / 提交 N 张未注册」** — 十有八九不是照片的问题。
老版本每 60 张拼一个 `multipart/form-data` 大包，这种请求体有两个坑：发出去过就不保证能重放
（重试经常发出 0 字节的空包），以及中途有一张读不出来就整批断流；服务端解析不出文件字段，
只能回 `HTTP 422：没收到图片文件（files）`，几千张换来满屏同一个错。

底库这条路现在整个换掉了：**一张图一个请求，请求体就是图片原始字节**，文件名走 URL 参数，
服务端没有任何表单要解析，`Blob` 也随时能重发。接口是 `open`（建任务）→ `push`（每张一次）→
`close`（收尾落盘），每张各自重试 4 次，失败只退回那一张。真撞上发不出字节的窗口，
第一张就报「这张浏览器没发出内容（0 字节）」并点名是哪个文件，不再让它变成一堆含义模糊的 422。

要复核当时到底发生了什么，看服务端日志里
`参数校验失败 ... content-length=? content-type=? ua=?` 那一行；
`content-length=0` 就是浏览器压根没发内容，最典型是在 **Codex 内置预览窗口**里操作，
换 **Safari 或 Chrome** 直开 `http://127.0.0.1:8617`，或者干脆用**导入本机目录**。
点「开始注册 / 开始评测」前还会先打一次 `/api/preflight` 自检，连 1×1 的小包都送不到 1 字节
就当场停下，不会让人对着几十屏同样的报错干等。

**几千张底库怎么灌最快** — 别走浏览器上传，用第 2 步的**导入本机目录**：填底库文件夹的绝对路径，
服务端直接读盘，98 张 3.2 秒，几千张几分钟灌完，还不会踩到「请求体是空的」这类浏览器环境问题。
部署到 RK3588 时照片本来就在板子上，这条会是默认用法。探针一次几十张，继续拖进来就行。
注意这个接口会读服务端本机的任意目录（评测机就是你自己那台机器），别在公网共享机器上开放它。

**提示「N 张图片大小都是 0，浏览器没真正读到文件」** — 换浏览器：用 **Safari 或 Chrome** 直接打开
`http://127.0.0.1:8617`，不要在 Codex 的内置预览窗口里拖文件（那里拿到的常常是占位符）。
拖进来后先看第 2 步的合计体积，几千张应该是几个 GB，显示 0 MB 就是没读到；
这时候改用**导入本机目录**最省事。

**报错里只有一句 "Load failed"** — 那是 Safari 的通用网络错误，正文一个字节都没发走。
现在报错会同时给出四条读法各自的原话（`读盘失败：常规读超时…`），服务端日志里也留一份。
最常见的两个原因：①**这批是拖进来的**——Safari 对拖拽拿到的文件读盘权限特别容易失效，
改用「选择文件 / 选择文件夹」按钮重新选一次就好；②照片本体在 iCloud/网盘里没下载下来，
先在访达里确认能直接打开（或下载到本地）。报错文案会自动分辨这批是拖的还是选的，
给出对应的那条建议。

**探针点「开始评测」显示「评测失败」** — 现在这行后面会跟具体原因，例如
「24 张探针图一张都没传上去，原因：xxx」。服务端日志只看得见 `preflight`/`probe/open`
两个 200，断点其实在浏览器里：图片选上了但页面读不到磁盘内容（iCloud/网盘没下载、
外置盘弹出、从预览窗口拖进来的占位符都算），于是一张都没发出去。
两处加固：读图先 `File.arrayBuffer()`，不行再换 `FileReader`，两种都读不到就
**把 File 本身交给 fetch 直接发出去**（浏览器发文件走的是和表单上传同一条路，
比 JS 读盘更容易成功），发不出去的那张会带上服务端回的原话；页面里 catch 到的
异常同时 POST 到 `/api/clientlog`，日志里落成
`浏览器报错 [probe_run] ... | UA=...`，不用再靠猜。照片本来就在这台机器上时，
用「评测本机目录」完全绕开浏览器上传。

**探针点「开始评测」一直停在「评测中」不动** — 有三种可能，现在都会在 1~2 分钟内给出结论，
不再无限等：读图四条路（常规读 / 备用读 / 对象地址读 / 解码重编码）截止钟分别是
20 / 8 / 8 / 12 秒——第一条是真正常用的读法，给足时间，免得把"读得慢"误判成"读不到"；
每次上传自带 10~20 秒截止钟（浏览器连取消信号都不理时，页面自己那只计时器照样兜底）；
整批上传再套一只总闸（约 90 秒 + 每张 1.2 秒，上限 30 分钟）。到点后：一张都没传上去就直接报错并把下一步说清楚，
已经传上去一部分就先把这部分评完。按钮上每秒刷新
「上传 3/40 · 12 秒…」，卡在哪一步一眼看得见。

**探针偶尔固定挂一张、每次还不是同一张** — 三次实测分别卡在
`080531_793_2` / `081206_972_7` / `081713_201_2`，文件在访达里都打得开，底库和抓拍
每一张都带同样的微信 quarantine 标记（不是权限差异）。判定为**多路并发读盘把 Safari 的
读通道挤爆**造成的间歇失败，不是文件坏了。三层处置：①并发降到 4 路；②首轮没送出去的那几张，
等并发停下来后**自动单发补送两轮**（间隔 900ms×轮次，总预算 90 秒），服务端 `/api/probe/push`
按文件名去重，重发只覆盖不重复计数；③补送救回来的会往 `/api/clientlog` 记一条
`probe_retry_ok`，日志里能看见「补送成功」。真救不回来的那几张，名字和下一步怎么办
**会钉在待办区**（不再只写在一闪而过的提示里），不用整批重来。反复出现就改用**评测本机目录**。

根因还是老问题——Safari 拿到读不动的原图会把请求一直挂着（请求头发出去了、正文一个字节都不来），
`File.arrayBuffer()` 既不返回也不报错。最稳的做法仍是**评测本机目录**。

**换识别模型后指标全乱** — 底库按模型分开存，换模型后要在第 2 步重新注册一次。

**合影里的脸全都没算进指标** — 那些脸真值为空（不认领是正常的）。要么在逐脸真值框里补标，要么只看"合影同框被放行"这一项。

**贴脸大头照检不到** — 默认会自动用 640 输入 + 更低阈值重试一次，重试过的记录上会标"首检失败，已用更大输入重试检出"。想强制只检测就选"强制检测"模式。

**小脸 / 远距检不到** — 检测输入调到 640，或降低"忽略小于"的像素门槛。

**同一个底库文件夹不小心拖了两次** — 不会膨胀：同一个人的同一张源图按 tid 原地替换，只保留一份模板。重复模板会把"同人互配"分数撑虚高，把阈值建议带偏，所以这里必须去重。

**Recall@k 拖阈值一点不动** — 正常，而且是设计如此。Recall@k 只看真值有没有被捞进前 k，跟放行阈值无关；要动它得换识别模型、加底库照片或调大检测输入。

**注册完人数从几千变成 1** — 规则选错了：底库是一张图一个人平铺的，却选了"文件夹名"，整批人会被并进根目录那一个名字下。把"人员 ID 来源"改回"文件名即人名"重新注册即可，注册完的"需复查"也会点名提示。

**底库文件名叫 `张三_0001_aug0.jpg`，"去序号"不认** — 去序号只处理结尾是数字的名字（`张三_0001.jpg`）。带 `_aug0`、`(1)` 这类尾巴的，用"文件夹名"或"文件名前缀"（分隔符填 `_`）。

**底库上传到一半断了** — 不会再整批作废：一张一个请求，单张失败先自动重试 4 次，仍失败就把**那一张**记下来继续传后面的；但**连续三张报同一个错就立刻停止**（同样的问题重试到第 30 次也不会突然成功），剩下的图片全部退回待注册列表并提示"点开始注册续传"。服务端排队有上限（48 张），推理慢于上传时浏览器自然等待，几千张原图不会在服务端内存里堆成几百 MB（RK3588 上只有几 GB）。进度条按总量显示"已送出 / 已注册 / 模板数"。页面刷新或 3 分钟没有新图片进来，服务端会把已收到的先存好，不会把线程和内存一直挂在半路上。

**改了代码但浏览器还在用旧页面** — 旧页面配新服务端最容易看出来的症状有两个：点"开始评测"报 `Cannot read properties of null`（新代码去取旧页面里不存在的控件），或者底库上传满屏 `HTTP 422：没收到图片文件（files）`（旧页面还在拼 multipart，新服务端只认逐张原始字节）。现在服务端每次发首页时都会把三个静态文件的修改时间拼成版本号写进去：`/static/app.js?v=<版本号>`、`/static/style.css?v=<版本号>` 和 `<meta name="app-build">`，`/` 带 `Cache-Control: no-store`、`/static/*` 带 `no-cache`，浏览器只能整套（HTML / JS / CSS）一起换，拼不出半新半旧的页面。页面加载时还会把 `<meta name="app-build">` 和 `/api/env` 返回的 `build` 对一遍，对不上就直接提示"浏览器用的还是旧版页面，请按 Cmd+Shift+R 强制刷新"，不用你猜。

**探针批次全是"无真值"，要一张张手点** — 探针默认就按**文件名即人名**认人（与底库同口径），`cam1/张三.jpg` 里那个 `cam1` 抢不到人名。只剩一种情况会全批没真值：探针文件名是 `IMG_0001`、`1792052059096` 这种相机自动编号，既对不上底库也认不出人，宁可不标也不造假。要么在结果页逐张补标，要么把探针图按人改名（或按人分文件夹，再把"探针真值来源"切到"文件夹名优先"）重跑一次。

**注册和评测能不能同时进行** — 可以。注册在后台线程跑，评测请求在线程池里跑，两边共用底库的锁；实测边传 98 人边连跑 4 批评测，全部 200，没有互相读到半个库。

**磁盘上还留着以前的批次报告，下拉里却找不到** — 那是孤儿报告：`data/probes/<批次>/` 里的探针图没了，只剩 `reports/probe_*.json`，启动时读不回来，界面上也就永远没机会删它。第 3 步点**清空历史批次**会连这类残留一起扫掉；命令行导出的 `cli_*.json` 不在删除范围内，要留要删自己定。

**端口被占** — `PORT=9000 ./run.sh`。

**界面是英文/中文混着** — 界面文案是中文，指标名保留 Rank-1 / Recall@k 这些行业通用叫法。
