# RK3588 万级人脸 1:N 识别 — 方案筛选与排序

> 目标：本地（RK3588）在约 1 万张底库中快速检索出对应身份，要求**速度快 + 准确率最高**。
> 数据核实时间：2026-11-06，来源为 InsightFace 官方仓库文档与官方 benchmark。

## 一、结论排序

### S 级（直接选型）

| 排名 | 方案 | 1:N 精度 | RK3588 速度 | 工程成熟度 | 商用许可 |
|---|---|---|---|---|---|
| 1 | **InspireFace + Gundam_RK3588** | 高（官方 R50 级特征） | 优（官方 NPU 包 + RGA） | 最高：SDK 自带 1:N 检索 FeatureHub、跟踪、质量评估、活体 | 代码开源，**模型非商用** |
| 2 | **自研：InsightFace buffalo_l / antelopev2 + 自转 RKNN** | 最高（MR-ALL 91.25% @FAR 1e-6） | 优（需自己做 RGA/MPP 与量化） | 中：流水线全自己写 | **模型非商用**，需向 InsightFace 授权 |

### A 级（可参考架构 / 特定场景）

| 排名 | 方案 | 定位 | 主要问题 |
|---|---|---|---|
| 3 | InsightFace 官方 `server/`（GPU 检索服务） | 中心端 1:N，官方实测 10M 向量 Top-5 p50 = 3.84 ms（INT8，RTX 5090） | 需 CUDA GPU，不能跑在 RK3588 端侧 |
| 4 | `040518/rk3568-face-recognition-qt`（SCRFD + MobileFaceNet + RKNN + Qt） | 代码干净、可直接抄流水线骨架 | MobileFaceNet 在万级 1:N 误识率偏高 |
| 5 | `ccl-123/RK3588-NPU`（YOLOv8-face + FaceNet + RGA + Qt + 5 级流水线） | RK3588 全流程参考实现，含 RKLLM 与 NPU 抢资源互斥 | 非商用许可；识别模型偏弱 |

### B 级（本次需求下不推荐）

| 方案类型 | 例子 | 淘汰原因 |

## 二、精度依据（ICCV21-MFR，MR-ALL @ FAR 1e-6）

同一评测协议下的 Rank-1 精度，这是"万级甚至百万级底库不错认人"最贴近的公开指标。

| 识别骨干 | 训练集 | MR-ALL | 相对算力 |
|---|---|---|---|
| **R100** | Glint360K | **90.66** | 1.00×（基准，248 MB） |
| R50 | Glint360K | 87.08 | 0.62×（166 MB） |
| R34 | Glint360K | 83.02 | 0.43× |
| R18 | Glint360K | 72.07 | 0.29× |
| R100 | MS1MV3 | 84.31 | 1.00× |
| R50 | MS1MV3 | 80.53 | 0.62× |
| **w600k_r50**（buffalo_l） | WebFace600K | **91.25** | 0.62× |

要点：
- **训练集比骨干更深更值钱**：R50 换 WebFace600K（91.25）就超过了 Glint360K 的 R100（90.66），算力只要 0.62×。
- 东亚人柱子最难，差距最大：R100/Glint360K 是 72.53，R50 是 66.81，R18 只有 47.83。国内场景必须看这一列。
- MobileFaceNet 系（buffalo_s / buffalo_sc）没进这张表，属于明显低一档，不适合万级 1:N 的低误识要求。

## 三、模型包构成（官方 `server/backend/insightface_server/models/packages.py`）

| 包名 | 检测模型 | 识别模型 | 向量维度 |
|---|---|---|---|
| buffalo_l | det_10g（SCRFD-10GF，640×640） | **w600k_r50** | 512 |
| buffalo_m | det_2.5g（SCRFD-2.5GF） | w600k_r50 | 512 |
| buffalo_s | det_500m（SCRFD-500MF） | w600k_mbf（MobileFaceNet） | 512 |
| buffalo_sc | det_500m | w600k_mbf | 512 |
| antelopev2 | scrfd_10g_bnkps | **glintr100**（Glint360K R100） | 512 |
| raccoon_s / raccoon_l | det_10g_wo | w600k_mbf / w600k_r50 | 512 |

- 全部识别模型输入 112×112，预处理 mean=127.5 / std=127.5；检测 mean=127.5 / std=128.0。转 RKNN 时这两个归一化系数必须照抄，错了精度直接崩。
- 官方给出的 buffalo_l 余弦阈值参考：**0.4078 @ FAR 1e-6**，可直接作为万级库初始阈值再本地标定。

## 四、速度依据：万级检索根本不是瓶颈

InspireFace 官方 benchmark（`cpp-package/inspireface/doc/Benchmark-Remark(Updating).md`）：

| 环节 | i7-9750H CPU | RV1126（弱 ARM + NPU） | RK3568 INT8（NPU） |
|---|---|---|---|
| 人脸检测 @320 | 8.49 ms | 22.64 ms | 25.11 ms |
| 对齐 + 提特征 | 6.14 ms | 42.35 ms | 9.07 ms |
| 轻量跟踪 | 1.96 ms | 8.86 ms | 11.22 ms |
| 1 对 1 比对 | 0.0002 ms | 0.0013 ms | 0.009 ms |
| **从 1 万条里检索** | **1.19 ms** | **31.27 ms** | 未公布（量级同上） |

结论：
1. **万级检索用暴力精确检索即可**，1 万 × 512 维点积在 RK3588 的 A76 核上约 2~4 ms，不需要 Faiss / HNSW（那是 10 万条以上才值得引入）。
2. **时间全在检测和提特征上**。RK3588 比 RK3568 快约 2~3 倍，检测 @320 约 8~12 ms，R50 提特征约 10~15 ms INT8。
3. **向量量化可以放心做**：官方实测 INT8 向量检索相比 FP32 精度只差 0.0011 个百分点（91.248% vs 91.249%），可省 3.7 倍内存。**但这说的是向量存储，不是模型 INT8 推理**——识别模型转 RKNN 时建议用 FP16，INT8 会明显掉点。

## 五、性能与精度同时拿到的架构

不要靠"换小模型"提速，要靠"稀疏提特征"：

1. 每帧只跑轻量检测（SCRFD-500MF/2.5GF @320~640，NPU 8~12 ms）。
2. 跟踪把多帧绑成同一轨迹，只在**质量最优帧**上触发一次 R50/R100 提特征（人脸对齐用 RGA 硬件 warp，别用 OpenCV CPU）。
3. 底库每人存 3~5 个模板（不同角度/光照/表情），检索取 Top-k 模板相似度均值排序。这一步对万级 1:N 召回的提升，通常大于把 R50 换成 R100。
4. 阈值本地标定：用 1 万底库 + 若干非底库真人跑一遍 FAR/FRR 曲线，不要直接照搬论文阈值。
5. 三核 NPU 用 `core_mask` 分进程绑核；若同时要跑 RKLLM 大模型，必须做 NPU 互斥调度（`ccl-123/RK3588-NPU` 有现成做法）。

预期：单路 1080p，检测 25~30 FPS，识别在 1 万底库上端到端 30~50 ms/次触发。

## 六、商用红线

- InsightFace 现在用**签名式模型授权**（`MODEL.LICENSE`，ed25519 签名）。官方仓库里 `buffalo_l`、`buffalo_sc`、`antelopev2` 全部标注 `grant: "non-commercial"`。
- InspireFace 的 README 明确：其开源模型与 InsightFace 要求一致，**仅限学术用途、禁止商用**；更高精度模型和商用集成需邮件联系 contact@insightface.ai。
- 若必须商用且不想谈授权：虹软 ArcFace ARM SDK（免费商用但需登记）是唯一能立刻落地的整包选择；或自训练 ArcFace（自己准备 WebFace/Glint360K 级数据 + 训练 R50），代码 MIT，权重自持。
- 注意：上一轮提到的 "buffalo_sc 是 MIT 可商用" 不成立，以官方 `MODEL.LICENSE` 的 `non-commercial` 为准。

## 七、建议动作

1. 先在 x86 上用 buffalo_l 与 buffalo_sc 各跑一遍你们真实底库的 1:N 评测（Recall@1 / FAR），确认可接受精度所需的最小骨干，别直接上板。
2. 同期拉 InspireFace 交叉编译到 RK3588，跑通 `Gundam_RK3588` 包与 FeatureHub 万级检索，用它做性能基线。
3. 若 InspireFace 精度或许可不满足，再走自研路线：buffalo_l 的 det_10g（INT8）+ w600k_r50（FP16）转 RKNN，RGA 做对齐，自写 C++ 流水线。
4. 并行确认商用许可路径：InsightFace 授权 vs 虹软 SDK vs 自训练，这条决定架构，建议一周内定。

## 九、精度差距有多大（ICCV21-MFR MR-ALL，all-pairs 1:1，FAR ≤ 1e-6）

| 识别模型 | MR-All | East Asian（东亚） | 用在哪 |
|---|---:|---:|---|
| **R18 / Glint360K** | **72.074** | 47.831 | ← **Gundam_RK3588 / Megatron 出厂** |
| R34 / Glint360K | 83.015 | 60.604 | 需自转 RKNN |
| R50 / Glint360K | 87.077 | 66.813 | 折中档 |
| R100 / Glint360K | 90.659 | 72.528 | antelopev2（glintr100） |
| **R50 / WebFace600K（w600k_r50）** | **91.249** | — | **buffalo_l** |

R18 的 INT8 还会在 72.074% 基础上再掉一点；w600k_r50 官方余弦阈值 **0.407787**（@FAR 1e-6），Gundam 出厂清单里 R18 的推荐阈值是 **0.32**，两者不可混用。

**为什么这 19 个百分点对「万张库」是决定性的**：1:N 检索要遍历整库，累计误识概率 = 1−(1−FAR)^(N−1)。

| 底库规模 | FAR=1e-4 时误识率 | FAR=1e-5 | FAR=1e-6 |
|---:|---:|---:|---:|
| 1 000 | 9.5% | 1.0% | 0.1% |
| **10 000** | 63.2% | 9.5% | **1.0%** |
| 100 000 | ~100% | 63.2% | 1.0% |

1 万底库想把「认错人」压到 1% 左右，**必须工作在 FAR≈1e-6**，而这正是 R18 掉得最狠的一档：72.07% vs 91.25%。若底库只有 1 千人，FAR=1e-5 即可，差距仅几个点——**库越大，R18 越吃亏**。国内人脸场景看 East Asian 列，同骨干间的差距还会进一步放大。

**代价核算**：R50 FP16 在 RK3588 NPU 上约 15~20 ms（INT8 约 8~10 ms），R18 INT8 约 3~5 ms；万级检索本身 ≈1 ms 不是瓶颈。**用 ~15 ms 换 +19 个百分点**，且单帧端到端仍在 20 FPS 以上——明确划算。

## 十一、三种落地形态（按性价比排序）

**首选｜自研 buffalo_l 流水线**
SCRFD-2.5GF(INT8) 检测 → RGA + HyPLmk/PFLD 对齐 → **w600k_r50(FP16)** 提特征 → 512 维 INT8 向量 + 暴力精确检索；底库每人 3~5 模板取 Top-k 均值；阈值以 0.4078 起标后本地重标定。

**折中｜保留 InspireFace 框架，只替换识别模型**（建议优先验证，工程量与精度的最优解）
沿用 FeatureHub / 跟踪 / RGA / 挑帧流水线，仅把包内 `feature:` 换成自转的 R50 RKNN，同步改 `__inspire__` 清单的 `name`/`fullname` 与 `similarity_converter.threshold`。两个必须验证的点：
1. w600k_r50 的预处理是 mean 127.5 / std 127.5，**必须在转 RKNN 时折进量化参数**，运行期才能沿用官方清单的 `mean: 0` / `norm: 1` + uint8 输入约定（清单里检测/识别全部是 mean0/norm1，就是这么做的）。
2. 包可能带资源完整性校验（`HFApiResourceBundleVerify`），**第一件事就是实测能否加载第三方模型**；清单本身是明文 YAML、未见签名段，可行性乐观但未验证。

**保底｜先跑通 S1 建基线，再升级识别**
直接用 Gundam_RK3588 打通链路与指标看板（1~2 周出可演示 Demo），若 1 万库 Recall@1 不达标，再按上一条只换识别模型，前期投入不作废。

## 十二、量化与精度的引用红线

- 官方 server 那张「INT8 只掉 0.0011 pp」的表（FP32 91.249107% → INT8 91.248005%）**说的是向量存储/检索精度**，原文明确标注 "not INT8 model inference"。**不能**据此推断 R50 模型转 INT8 也无损。
- 检测模型转 INT8 掉点通常很小；**识别模型对量化敏感**，先以 FP16 落地拿精度基线，再评估 INT8 + 校准集，且必须用你们自己的 1 万底库测 FAR/FRR。
- 所有官方 benchmark 均出自 PyTorch / ONNX Runtime 路径，切到 RKNN 后必然更低。**上板自测是唯一判据**，不要把论文/榜单数字当验收标准。

# 多轮交叉验证记录（第二轮 · 每条结论都换独立来源复核）

验证方法：同一结论至少找两个互不依赖的来源；估算值一律换成官方实测锚点重算。以下 4 条修正/加强前面的结论。

## 十三、修正一：R50 的真实耗时比我先前估的更低（结论更强）

先前写的是「R50 约 15~20 ms」，属估算。现用瑞芯微官方 `rknn_model_zoo` 基准表重算，该表按 **FPS** 给出各芯片实测值（注意列名是 `RK3588 @single_core`，即只用 1 个 NPU 核）：

| 官方实测（RK3588 单核 NPU，INT8） | FPS | 换算单帧 |
|---|---:|---:|
| resnet50-v2-7 @224×224 | 112.5 | **8.9 ms** |
| RetinaFace_resnet50_320 @320×320 | 50.0 | 20.0 ms |
| mobilenetv2-12 @224×224 | 458.8 | 2.2 ms |

**换算法**：ArcFace 的 iresnet50 在 112×112 输入下，主干第一级特征图同样是 56×56（ArcFace 用 3×3 stride1 stem + maxpool stride2，与 ResNet-50 的 7×7 stride2 + maxpool stride2 输出尺寸一致），算力与 resnet50@224 基本相等 → **w600k_r50 INT8 ≈ 9 ms/脸**（RK3588 单核）。

**三路交叉验证，彼此独立且互相吻合**：
1. 由 resnet50@224 实测 8.9 ms 反推 → R50 ≈ 9 ms。
2. 官方 V100 同硬件比值：R50 4.340 ms ÷ R18 2.013 ms = **2.16×** → R18 ≈ 4.1 ms、R50 ≈ 9 ms。
3. 由 InspireFace 官方 RK3568 实测「align+Extract = 9.07 ms」按 NPU 算力代际（RK3568 约 1 TOPS vs RK3588 3 核）折算 → R18 ≈ 3~4 ms，×2.16 → R50 ≈ 7~9 ms。

**结论修正**：从 R18 升级到 R50 的代价只有 **≈ +5 ms**（不是先前说的 +15 ms）。FP16 约 18 ms（RK3588 FP16 吞吐是 INT8 的一半）。**"精度换速度"这笔交易比原报告里写得还要划算。**

## 十四、修正二：识别模型 INT8 确实会翻车，且有现成解法（MMSE）

`040518/rk3568-face-recognition-qt` 是一份 **RK3568 实机量化回归报告**（2026-10-26，RKNPU 驱动 0.9.2 / RKNN-Toolkit2 2.0.0b0），做的正是同一条流水线（SCRFD 检测 + w600k_mbf 识别 + 余弦匹配），其数据独立印证并加强了我先前的提醒：

| 模型 | 指标 | 结果 | 判定 |
|---|---|---:|---|
| SCRFD INT8 | 12/12 图人脸数与 FP16 一致、IoU 中位数 0.9833 | 通过（门槛 0.90） | ✅ 检测转 INT8 安全 |
| MobileFaceNet **普通 INT8** | 64 样本最低 FP16/INT8 embedding 余弦 | **0.9735** | ❌ **未达 0.98 门槛** |
| MobileFaceNet **MMSE INT8** | 同上 | **0.9904** | ✅ 通过 |
| MobileFaceNet MMSE INT8 | 2016 对在阈值 0.45 的判定翻转 | 0 | ✅ 通过 |

要点：
- **「检测 INT8 安全、识别 INT8 危险」得到了实机证实**——原报告第十二节的判断成立。
- **新增可执行解法**：识别模型用 RKNN-Toolkit2 的 **MMSE 量化**（而非默认逐层量化），最低余弦从 0.9735 提到 0.9904。
- **验收门槛可直接照抄**：同输入 FP16/INT8 embedding 余弦最低值 ≥ 0.98 + 阈值判定翻转数 = 0，样本量 64 图 / 2016 对。
- 该项目的识别用的是 `w600k_mbf`（MobileFaceNet，弱一档），不是 R50——他们是在 RK3568 的弱 NPU 上做的妥协，不代表 RK3588 的选择。

**顺带推翻一个常见直觉**：MobileFaceNet 这类 depthwise 网络在 NPU 上**并不高效**——该项目实测 RK3568 上 MobileFaceNet FP16 要 20~23 ms/脸。折算到 RK3588 约 8~9 ms，**和 w600k_r50 INT8（≈9 ms）几乎一样快**，但精度差一个档（w600k_mbf 是 MobileFaceNet，远低于 w600k_r50）。**在 RKNN 上「用小模型省时间」的直觉不成立，dense 的 R50 才是对的。**

## 十五、加强：换识别模型在源码层面确认可行（不再是"乐观猜测"）

前一份报告写的是「可行性乐观但未验证」。现已读到底层实现，风险等级下降：

1. **打包工具是官方现成的**：`cpp-package/inspireface/tools/inspire_archive/archive_packing.py`，实现就是 `tarfile` 打包 + 去掉文件后缀，**没有签名、没有 MD5 写入归档**。
2. **校验器不涉及模型身份**：`cpp/inspireface/c_api/resource_pack_validator.cpp` 的 `HFValidateResourcePack` → `InspireArchive::ValidateContents()`，实际只做三件事：文件能被加载、`inferEngine`/`modelType` 是当前 SDK 构建支持的引擎、`fullname` 非空。遍历的是 **YAML 里自己声明的模型名**，不存在官方模型白名单或哈希锁定。
3. **官方文档明确把换识别模型当常规操作**：模型资源包一页写着「**更换识别模型后，重新生成特征库中的向量，并重新评估比对阈值**」，切换模型包一节又写「**识别模型发生变化后，还需要重建特征库**」。

剩余风险只剩「w600k_r50 转 RKNN 后数值是否对齐」这一项纯工程问题，属于半天能验完的范围。

## 十七、最终锁定方案（单一推荐，已去掉备选）

**InspireFace RK3588 SDK + Gundam 的检测/对齐不动 + 只替换识别模型为 w600k_r50**

分工：检测 SCRFD-2.5GF（160/320/640 三档，已 INT8 验证）、关键点 HyPLmkV2、RGA 加速、跟踪、挑帧质量、FeatureHub 万级检索——**全部沿用官方现成件**；唯一自研的是识别模型转换与回归。

预期指标（均有实测锚点，非拍脑袋）：检测 5~6 ms、关键点+对齐 1~2 ms、识别 ≈9 ms(INT8) / 18 ms(FP16)、1 万库检索 ≈1 ms → **端到端 16~26 ms/次触发**；识别率由 72.07% → **91.25%**（FAR 1e-6）。

首日验证清单（半天定生死）：
1. `w600k_r50.onnx` → RKNN，**先 FP16**，`optimization_level=0`，mean 127.5/std 127.5 折进转换参数。
2. 同一批对齐人脸图跑 ONNX 与 RKNN，要求 embedding 余弦最低值 ≥ 0.99。
3. 改 `__inspire__` 的 `feature:` 段（name/fullname）与 `similarity_converter.threshold`（0.32 → 以 **0.4078** 起标）。
